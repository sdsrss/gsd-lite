# 0.17.0 的遗留：研究存储的两个 LOW、离开再回来时的模式、state-update 的研究校验、e2e 偶发超时
状态：本地完成（fix/0.17-leftovers、test/e2e-fetch-timeout 未推送；推送 / PR / 合并待用户决定）

## 背景与目标

2026-10-21 用户在 0.17.0 发布后要求"继续完成剩余能做的工作，做完了分支要删了"。遗留来自
`tasks/specs/research-in-state-0.17.md` 的第二、三轮复审和发版报告。这次做其中能在代码里修的几项，
发版不在本次范围内（用户没有要求）。

main f863525 上的复现（`node repro.mjs <repo>`，脚本在会话 scratchpad）：

- R1：已有真实研究时，摘要写成 `" [BLOCKED] 研究来源不可用"`（前面多一个空格）的结果被存下，真实决策被替换。
- R2：已有真实研究时，`decision_index` 为 `{}` 的结果被存下，已记录的决策全部清空。
- R3：task 审查中 (`reviewing_task`, `current_review {scope: task, stage: spec}`) 上下文不足转 `awaiting_clear`，
  /clear 后 resume 返回 `dispatch_executor` 1.2，被打断的审查没有回来；刷新那条路径 (`inferWorkflowModeAfterResearch`) 会恢复它。
- R4：调试中 (`current_review.stage: debugging`) 暂停，resume 报 `resume_to: reviewing_task`。
- R5：`state-update` 写入 `research.decision_index: {"decision:a": null, ...}` 被接受；之后一次正常刷新
  `storeResearch` 抛 `TypeError: Cannot read properties of null (reading 'summary')`。

级别：L2（都是让行为回到文档写明的意图：研究不因 researcher 偏离提示词而丢失、离开再回来时回到原处、
state-update 不写下 validateState 拒收的 state）。改动涉及 MCP 工具描述和随包提示词（resume.md、state-diagram.md），
按用户全局规则这类改动属于 L3；用户这次的指令点名了这些遗留项，作为本次授权，记在这里。

## 方案

- 受阻识别：`summary.trimStart().startsWith('[BLOCKED]')`。
- 空索引：记录里有真实结论、新结果的 `decision_index` 为空 → 拒收，报错写明"返回完整的决策集"和放弃研究的出路；
  记录为空或只有受阻占位时照常存。resume.md 已有"其他校验错误把原文交给 researcher 重派一次"，不用改。
- 模式函数 `workflowModeForReview(review)`（constants.js）：
  - 没有审查，或 `stage: debugging` → `executing_task`；
  - 带审查阶段 (`spec` / `quality`) 以外的 stage → `awaiting_user`（用户还欠一个决定，如 `human_confirmation`、`review_retry_exhausted`）；
  - 其余按 scope：`phase` → `reviewing_phase`，`task` → `reviewing_task`。
  - 信任的是审查阶段这一小集合，不是 hold 的列表（记忆第 8 条）。
  - 使用方：`inferWorkflowModeAfterResearch`（刷新让 task 失效时仍丢掉审查）、`resumeAwaitingClear`、`paused_by_user` 的 `resume_to`。
  - `WORKFLOW_TRANSITIONS.awaiting_clear` 加上 `reviewing_task`、`reviewing_phase`。
  - resume.md 的暂停恢复改为写 `resume_to`。
- 校验：schema.js 抽出研究记录和 evidence 条目的检查，`validateState` 与 `validateStateUpdate` 共用。

  另一个是刷新函数里一行对现实 state 等价的分支，删掉。第二轮 13/13 被杀。
- e2e：克隆里 7 次全套（负载 4.5–21）全部通过；工作树上第 3 次全套复现：Layer B `npx --yes file://…tgz install` 180 秒超时，4 个子测试取消，结束时负载 1.1。
  空缓存安装 6 次：3 次 8–9 秒，另 3 次各有一两个 registry 元数据请求单独用了 13–33 秒。npm 源码：`fetch-timeout` 默认 300 秒、是单个请求的总时长，
  超时后按 `request-timeout` 重试（`make-fetch-happen/lib/remote.js`）。修法：测试里取 registry 的三步设 `npm_config_fetch_timeout=30000`，单独的纯测试分支。
- e2e 后续（推翻了"一个设置就够"）：在测试分支上单独跑 e2e-install，带着 30 秒设置仍在 180 秒超时一次。手动按测试方式跑 Layer B 的 npx 安装：
  - 卡住的是 install.js 为不带 lockfile 的 tarball 起的嵌套 `npm install`（会把 dev 依赖 biome 的各平台包元数据也拉一遍）；
  - 不设：10 次里 2 次到 300 秒仍挂着，4 个连到本机 HTTP 代理 `10.77.0.1:17890` 的 socket 已发请求、无回应；
  - 设 30 秒：6 次 0 次挂住（20–140 秒），日志有 ECONNRESET 后的重试；最慢一次里一个元数据请求单次 121 秒、无重试。
    `fetch-timeout` 从拿到 socket 才开始计时（minipass-fetch `req.once('socket')`），连接超时默认 0，所以等代理隧道的那段不受它约束（推断）。
  - 受控复现（本地代理对一个包的元数据永不应答）：默认 200 秒仍挂；30 秒时第 2 次请求成功，49 秒装完。
  - 结论：根源是本机代理偶发不回话，不是负载；30 秒设置缩小了失败面但不能消除。已提交为部分缓解（test/e2e-fetch-timeout 0c441ff），余下记为遗留。
  - 曾用 `npm exec` 核实环境变量传递，被安全 hook 拦下（误判 `node` 为未钉版本的包），没有绕过；改读 `@npmcli/run-script/lib/make-spawn-args.js`（`...process.env, ...env`）确认会传下去。
