## 方案

- (f) `update()` 在合并前检查 `phases[i]` 和 `phases[i].todo[j]` 必须是对象，否则 INVALID_INPUT 并点名位置。性质测试对每个 canonical 字段都问"会不会抛"，只有这两处会。
- (c) 五处用 validateState 错误回答的地方（带校验的 read、update、patchPlan、phaseComplete 两个分支）在错误涉及 research 时附上出路
  `state-update (research: null)`；调用本身在写 research 时不附（那时错的是这次写入）。没有改"已有错误也拦全量校验"这一行为。
- (d) storeResearch 把不是对象的 `decision_index` 当空记录，与 a4561e6 对坏条目的处理一致。只处理 0.17.0 的 state-update 能写出的形状（字符串/数字/数组），
  `research` 本身不是对象只有手改文件才会出现，不处理。
- (e) 受阻识别改为正则：前导空白、零宽字符、`*` `_` 反引号，半角/全角/方头括号，括号内空格，不分大小写。漏认是静默丢研究，多认是有理由的拒收，所以放宽；
  对照测试确认只是提到 blocked 的真实结论照常存。
- install：运行时 package.json 删 devDependencies；四处运行期 npm 调用里缺 `--no-audit --no-fund` 的三处补上。

## 决策与进展

- 2026-10-21 statusline 问题（只解释，不改代码）：用户本机是 0.13.0 手动安装，不是插件。6 个命令在 `~/.claude/commands/gsd/`，Claude Code 把命令和 skill 合并列出，所以一个命令一项。
  `skillOverrides: user-invocable-only` 只禁止模型自动调用（官方文档：取值 on / name-only / user-invocable-only / off），对 hook、MCP、statusline 都没有作用。
  statusline 是 code-graph 的组合脚本按 `~/.claude/statusline-providers.json` 调用 gsd 的 `gsd-statusline.cjs`，中间一段"Opus │ gsd-lite"里的 gsd-lite 是目录名（在 /tmp 下显示 tmp）。
  要彻底关掉：运行 0.13.0 的卸载器，或换成插件安装（`/plugin disable` 一处开关）。改 `~/.claude/settings.json` 属 hard AUTH，交给用户。
- e2e 方向一（去 devDependencies）实测：npx 流程里嵌套 `npm install` 的请求从 13 个降到 2 个（8/8 次），少的 11 个都是 biome 及其平台包元数据；一次基线里其中两个请求用了 22 秒和 45 秒（ECONNRESET 后重试）。
  安装出的树相同（111 个 package@version，overrides 生效）。整个 npx 安装时长没有可测的变化（基线 12–57 秒，去掉后 10–96 秒，n=8），npx 自己的约 192 个请求占主导。
  决定：做，作为清理，不当作超时修复。
- e2e 方向二（预热缓存）：带 30 秒 fetch-timeout 后 16 次 npx 安装 0 次超过 180 秒；预热会改变本地 Layer B 测的东西（不再从 registry 解析），且 npx 的 `_npx` 目录按 spec 复用有测到旧 tarball 的风险。决定：不做，复发时再看。
- 排查中的新发现：本次 pre-commit 连续三次失败，hook 只打印栈尾。改 hook 点名失败测试后，第三次点名为 **Layer A "npx install E2E (npm ci fallback)"**：install.js 55 秒 `spawnSync node ETIMEDOUT`，
  输出停在"Installing runtime dependencies"。单独复现该分支：负载 29 时 1.5 秒完成，0 个 GET、1 个 POST（`security/advisories/bulk`）。install.js 的 `npm install` 分支带 `--no-audit`，`npm ci` 分支没带；
  launcher.js（插件模式 MCP 首次启动前安装依赖，60 秒超时）和 auto-update 也没带。都 pipe 输出，审计结果没人看。补齐三处，并加了覆盖全部发布文件的类级测试。
  这也更正了 0.17 遗留 spec 里两次"推断是 Layer B"的说法（未被证实）。
- 本机负载：排查期间负载 13–31，来自另一个项目并发的构建（`npm rebuild better-sqlite3`、eslint），npm 只保留最近 10 个日志，最早那次失败的 npm 日志已被轮转掉。
- gate-replay 对 e2e-install 的判定不可信（早于本次，未改）：回放树里 node_modules 是符号链接，基线 install.js 的 copyDir 先 mkdir 再 cpSync 一个符号链接 → EEXIST，
  所有复制 node_modules 的 Layer A describe 被取消；脚本只读 `# fail`，于是对照回放报"VACUOUS — 35/35 passed"，实际 pass 14、cancelled 21。
  本次 e2e-install 的区分性证据改用：原始回放里 Layer B 两个 devDependencies 断言失败 + 在真实检出里手动回退源码的两次红（devDependencies 断言原文、advisories POST 原文）。
- (a)(b) 的建议（不在本次实现）：它们与第 2 项同根——`planning` 和 `paused_by_user` 是仅有的两个不能从 `current_review` 或任务事实推回的模式，叠上另一个模式后"回到哪里"就丢了。
  分别修补（拒绝 planning→paused、paused→awaiting_clear 两条边）会在之后的统一设计里被替换。建议下一个小版本一起做：服务端在进入 hold 时记下返回模式，
  三处"写回 executing_task"和 (a)(b) 都从它恢复。要改状态机、resume.md / stop.md / execution-flow.md 和上下文监视器的提示，属 L3，等用户决定。
- 提交拆分：每个逻辑改动一个提交；拆分时按 runbook Trap 21 用 `stash --keep-index` 让 pre-commit 测提交内容本身。
