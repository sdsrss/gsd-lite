## 背景与目标

2026-10-21 0.17.1 发布后，用户授权并要求"继续完成剩余工作……深入思考，给出科学准确的建议，然后按你的建议执行"。
本次是建议里的"下一个补丁版"：先修小而独立的缺陷，状态机、`/plugin disable`、显式受阻字段三项 L3 设计放 0.18.0（`tasks/specs/0.18.0.md`）。

main 24ffce0 上的复现（脚本在会话 scratchpad：`repro-state.mjs`）：

- P1 代理：本机必须走 `HTTPS_PROXY`。`fetchLatestRelease()` 不设 `NODE_USE_ENV_PROXY` 时 3007 ms 返回 `null`（进程约 20 秒后才退出），设为 1 时 1.1 秒返回 0.17.1。
  失败不留任何原因：`update-state.json` 只写 `lastCheck`，没有通知。用户本机 0.13.0 因此一个月没更新。
- P2 `syncPluginCache`：插件缓存安装没有 lockfile，`npm install --omit=dev` 仍解析 devDependencies（0.17.1 复审实测 203 对 192 个请求）。
  追查：它在 4fc8641（2026-03-17 10:47）加入，而 651fab1（同日 01:43）已让插件安装只通知不下载。经 `checkForUpdate` 只有"git 检出 + `gsd update --force` + 装了插件"能走到它，且它改写 Claude Code 自己的 `installed_plugins.json`。
- P3 被拒的写入写了归档：evidence 满额时，`update({current_phase: 2, evidence: {… passed: 'not-bool'}})` 返回 VALIDATION_FAILED、state.json 不变，但 `evidence-archive.json` 已写出。
  `phaseComplete` 同样先修剪（写归档）再校验。归档有上限，重复写入的活条目会挤掉真正归档过的旧条目。
- P4 `update({phases: [{id: 1, phase_review: 'ok'}]})` 成功，写下 `{"0":"o","1":"k","status":"pending",…}`；`phase_handoff` 同样。
- P5 gate-replay：前置钩子失败时子测试是 cancelled，TAP 报 `# fail 0`、`# cancelled 2`、退出码 1，脚本只读 `# fail`，给出 VACUOUS。
  回放树的 node_modules 是整个目录的符号链接，install.js 的 `mkdir` + `cpSync` 对它报 EEXIST，e2e-install 的 Layer A 因此全部取消。

级别：L2（P1–P4 都是让行为回到已写明的意图：自动更新本应生效、被拒的调用不写任何东西、补丁按对象合并；跨 hooks 与 state 两个模块）。P5 是不随包发布的开发工具。

## 方案

- P1：官方文档（nodejs.org http.html、undici 文档）：内置 fetch 在 v22.21.0+ / v24.0.0+ 读 `NODE_USE_ENV_PROXY`，只在启动时读；
  `http.setGlobalProxyFromEnv()` 从 v24.14.0 / v25.4.0 才有；Node 20 都没有。
  - session-init 第 5 阶段：`env: { NODE_USE_ENV_PROXY: '1', ...process.env }`（用户显式的值覆盖默认）。环境里没有代理变量时这个变量无作用（Node 启动时直接返回）。
  - `gsd-auto-update.cjs`：`envProxyRoute()` 返回 `direct` / `startup` / `runtime` / `unsupported` / `opted-out`，`runtime` 时调用一次 `setGlobalProxyFromEnv()`；
    真实的两个网络入口（`fetchLatestRelease`、默认 fetch 的 `downloadAndInstall`）先调用它。
  - 失败原因：`fetchLatestRelease` 失败返回 `{ error }`（403 仍返回 `false`），原因只由错误码（`/^[A-Z][A-Z0-9_]*$/`）、HTTP 状态、超时秒数和代理路由拼成，
    从不放原始错误文本（代理 URL 可能带账号密码，这段文本会进入模型上下文）。
  - `update-state.json` 记 `checkFailure: {since, count, reason}`，成功即删除。count 到 3 时写通知，之后每 7 次再写一次（检查最多一天一次）。
    SessionStart 第 4 阶段显示 `check_failed`，原因按字符白名单和长度上限清洗后输出。
- P2：删除 `syncPluginCache` 与只被它用的 `pruneOldCacheVersions`。插件缓存归 Claude Code 管，插件安装本来就只通知（`claude plugin update`）。
- P3：`_pruneEvidenceFromState` 改为纯内存计算，返回要归档的条目；归档文件由 `_writeEvidenceArchive` 在写 state.json 之前、校验通过之后写。四个调用方都改。
  归档先于 state 的顺序（R-20 的崩溃语义）不变。
- P4：`update()` 入口检查：`phases[i]` 带 `phase_review` / `phase_handoff` 而值不是对象 → INVALID_INPUT。
- P5：解析 TAP 每条结果的 `failureType`，`cancelledByParent` 不算失败也不算通过；没有真实失败而有取消 → INCONCLUSIVE（退出码 2），并列出失败的钩子所在的 suite。
  VACUOUS 的计数用 `# pass`。回放树的 node_modules 改为真实目录，逐项符号链接到检出的包。

  装插件会带回每会话 3 个 hook 和 MCP 工具描述。重装是两条命令。
- 发两个版本而不是一个：0.17.2 小而独立、风险低，先把代理修复送出去，不等 L3 设计；0.18.0 单独复审。
- P1 实测：本机经代理请求 GitHub API 22 次，20 次 1.01 秒内返回，2 次在 undici 10 秒连接超时处卡住（代理偶发不回话，不是慢）。3 秒超时不改：
  加长救不了卡住的请求；连续 3 次才通知，单日卡住不会误报。不加重试：检查一天一次，卡住只是推迟一天发现新版本。
- P1 复现中的发现：修复后不设变量的路径（Node 26 运行时开关）第一次就超时 3 秒，接着两次成功——就是上面的偶发卡住，不是代码问题（同一进程单独调用 setGlobalProxyFromEnv 788–1021 ms 成功）。
- doctor.md 是随包提示词（按用户规则属 L3）：加一行 `check_failed`，与其他通知种类并列；用户本次的授权覆盖。测试从写入方源码导出种类，检查 SessionStart 和 doctor 都认。
- 我自己测试的空洞（变异找到）：路由测试直接调 envProxyRoute，删掉两个网络入口里的调用全绿 → 补接线测试（568ed83）；fetchLatestRelease 的 HTTP 错误改回 null 存活（M24）→ a81250f。
- `{"toString":1}` 一类值（自有的 toString 不是函数）：不修。只有模糊测试能产生，失败是响亮的（Tool execution failed）且什么都不写；
  修它要审计校验器里每一处字符串化（几十处模板字符串），成本与收益不成比例。0.17.1 已把测试名改成它实际覆盖的范围。
