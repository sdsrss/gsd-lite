## 方案

### 1. hold 的回程：`suspended_modes`

- 新的服务端字段 `suspended_modes`：被当前 hold 们打断的模式，最近的在最后。可读（READABLE_FIELDS），不可由 `state-update` 写（不在 CANONICAL_FIELDS）。
- 规则（纯函数 `nextSuspendedModes(stack, from, to)`，模式变化时由每个写入点调用）：
  1. `to` 等于栈顶 → 出栈（回到被打断的模式）；`to` 是工作模式时清空。
  2. 否则 `to` 是 hold → 把 `from` 压栈。
  3. 否则（去了别的工作模式或 completed/failed）→ 清空（放弃了被打断的东西）。
  - hold 集合由可信的工作/终止集合反推：工作模式 `planning`、`executing_task`、`reviewing_task`、`reviewing_phase`，终止 `completed`、`failed`；其余都是 hold（记忆第 8 条：列可信集合）。
  - 栈深上限 8，溢出丢最旧的。
- 不变式：工作模式或终止模式下栈为空；validateState 检查，写入点漏了规则会被拒收（响亮）。
- 回到栈顶的转移总是允许（不受转移表限制）——这就是"回到原处"，例如 `paused_by_user → planning`。另加 `planning ↔ awaiting_clear` 两条边（规划中上下文不足）。
- 读取：`paused_by_user` 的 `resume_to`、`awaiting_clear` 的恢复、所有 hold 响应的 `resume_to` 都取栈顶；栈空（旧 state）时退回 `workflowModeForReview(current_review)`。
- 研究刷新（storeResearch）仍由 `inferWorkflowModeAfterResearch` 决定去处（使 task 失效时丢掉审查是有意的），写入后按规则 1/3 维护栈。
- preflight：`paused_by_user`、`planning`、`awaiting_user`、`awaiting_clear` 下不执行任何覆盖。暂停时什么都不该变；规划时计划文件本来就在改；
  等用户时用户的决定在先；等 /clear 的恢复会回到原模式再 resume，那时 preflight 照常。原有的 L3 人工确认豁免被这条覆盖，保留为显式检查。
- 离开 `planning` 去 `executing_task` 时刷新计划哈希（与离开 `replan_required` 相同），否则计划修订刚完成就报一次漂移。
- 提示词：reconcile / replan 的自动处理、放弃研究的出路都改为写响应里的 `resume_to`；暂停可回到 planning。

### 2. `/plugin disable` 关掉 gsd

- `hooks/lib/hook-registry.cjs` 新增 `pluginDisabled(claudeDir, cwd)`：存在 gsd 插件记录（`gsd@*`；project/local 作用域须指向当前项目），
  且按 local > project > user 的优先级第一个写了 `enabledPlugins[id]` 的设置文件里值不是 `true` → 禁用。没有记录、或没有任何文件写这个键 → 不算禁用（照常运行）。
- 三个 hook 的 settings.json 副本：`pluginServesHooks || pluginDisabled` 时退场。插件自己的副本：Claude Code 不加载被禁用插件的 hook，不涉及。
- statusline（只由 npx 安装注册）：禁用时不输出、不写桥接文件和 `.context-health`。
- MCP server：不是以插件身份运行（无 `CLAUDE_PLUGIN_ROOT`）且禁用时，`tools/list` 返回空、调用一律拒绝并说明。helper 按两个候选路径加载（npx 布局 `~/.claude/hooks/lib`、仓库/插件布局 `../hooks/lib`），都加载不到就照常运行（宁可多跑，不静默零运行）。

### 3. 研究受阻：显式 `blocked`

- `validateResearcherResult`：`blocked` 必填且为布尔值。
- storeResearch：`result.blocked === true` 即受阻；已记录的研究算"真实研究"当且仅当有决策且 `research.blocked !== true`。存下受阻结果时 `research.blocked = true`，存下真实结果时为 `false`。
- `blocked: false` 而某个决策摘要以规范前缀 `[BLOCKED]` 开头 → 拒收并说明（自相矛盾，只认规范写法，不再放宽）。
- migrateState：已记录研究没有 `blocked` 字段时，全部决策摘要都匹配旧前缀正则 → `blocked: true`，否则 `false`。旧正则只留在迁移里。
- 提示词：researcher.md 结果契约（正常与受阻两个示例），resume.md、research.md，server.js 的 `orchestrator-handle-researcher-result` 描述。

## 决策与进展

- 2026-10-21：用户授权进入 L3 实现（"该我授权的授权……按你的建议执行"）。走 §4.FULL-lite（无鉴权/支付/加密，模块 ≤3：src/tools、hooks、随包提示词）。
- 为什么是栈而不是单个字段：hold 会叠 hold（暂停上 /clear、等用户上暂停、reconcile 后 replan），每个 hold 都该回到它打断的那个模式。单个字段在第二层就丢了第一层。
- 为什么 preflight 在四种模式下不执行，而不是靠栈把覆盖"还原"：脏 phase 回滚直接写工作模式并清 `current_review`，按规则 3 会清空栈；
  而这四种模式里覆盖本身就不该发生（F 的三种都是服务端越过用户）。
- 插件启用时 settings.json 的 MCP 不退场：退场的代价是插件 MCP 启动失败时零工具（静默）；重复是可见的（记忆第 4 条）。
- preflight 实现为可信集合 `PREFLIGHT_MODES`（三种工作模式 + reconcile/replan/research_refresh 三种 hold），而不是方案里写的"四种模式下不执行"的跳过名单：
  跳过名单漏掉的新模式会被覆盖（记忆第 8 条：列可信集合）。效果覆盖方案里的四种，另外 completed/failed 也不再被覆盖。
- 研究受阻的识别正则 `BLOCKED_TAG` 只留在 `migrateState`（旧记录一次性标记）和"`blocked: false` 却写占位摘要"的矛盾检查里；
  矛盾检查用迁移同一个正则，而不是方案里的"只认规范前缀"：旧正则能认出的写法若在 `blocked: false` 下放行，会把占位存成真实研究。
