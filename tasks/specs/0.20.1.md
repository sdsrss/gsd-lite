# 0.20.1：更新器不装当前 Node 跑不了的版本
状态：进行中

## 背景与目标
0.20.0 把 `engines.node` 提到 `>=22.0.0`，但 install.js 和 hooks/ 里没有任何 Node 版本检查（0.20.0 评审 MEDIUM-2，D#645）。npm 的 EBADENGINE 只在 npx/npm 取包时出现；每日后台更新和插件更新都不经过它。所以等到第一个真正用到 Node 22 特性的版本发布时，Node 20 用户会被静默更新到跑不起来的版本。

检查必须放在执行更新的那个旧版本里，所以要在那个版本之前发出去，并且留出时间让每日检查把各安装带到 0.20.1。2026-11-02 用户说"按你的建议执行"，建议就是本文件的范围。

## 范围
- 做：
  - npx/全局安装：后台更新和 `npx gsd-lite update` 在运行 install.js 前读新版本的 `engines.node`，当前 Node 不满足就不装，并给出提示。
  - 插件安装：更新由 Claude Code 执行，所以只改提示：新版本要求更高的 Node 时，不再提示"运行 claude plugin update"，改为提示先升级 Node。
  - 会话提示、`update` 命令输出、`/gsd:doctor` 三处都说明这种情况。
  - CHANGELOG 0.20.1；顺手把 0.20.0 的日期从 2026-11-01 改为实际发版日 2026-11-02。
- 不做：
  - 将来用到 Node 22 特性的版本自己在旧 Node 上报出清楚的错误（launcher.js / hooks 启动检查）：代码在新版本里，不受时间限制，做那个版本时再加。
  - LOW-2（CI 测 22.0.0）：要改 CI 配置，需要单独授权，另需修 27 个测试工具层面的失败。
  - D#645 里的其余 LOW（LOW-1、LOW-4、两个项目级插件互相吞提醒、`pluginServesHooks` 只读 `record[0]`、用户级插件加遗留 `failed` 提醒、0.7.6 及更早的 npx 安装 `update --force` 装不上）：只影响少见的安装组合或只多打一次提示，继续推迟。

## 验收标准
- [ ] AC1：`unmetNodeRequirement(range, version)` 只认 `>=X.Y.Z`；版本低于它时返回规范化的范围，否则返回 null；其他写法也返回 null — 验证：auto-update 单元测试（先红）
- [ ] AC2：npx/全局安装：新版本的 `engines.node` 不满足时，install.js 不运行，返回 false，通知是 `needs_node`，状态里记 `needsNode`；满足时照常安装 — 验证：用真实 tarball 夹具的 downloadAndInstall 测试 + checkForUpdate 测试（先红）
- [ ] AC3：插件安装：tag 上 package.json 的 `engines.node` 不满足时，通知是带 `action: plugin_update` 的 `needs_node`；读不到时退回原来的 `available` 通知 — 验证：checkForUpdate 测试（先红）
- [ ] AC4：节流时重放缓存，只要当前 Node 仍不满足，就带上 `needsNode`；`describeUpdateOutcome` 在三种情况（npx 刚检查、插件、缓存重放）下都说明需要的 Node 版本 — 验证：测试（先红）
- [ ] AC5：会话提示打印 `needs_node`（npx 和插件两种措辞）；目标版本已装上、或当前 Node 已满足时不打印；`updated` 通知不受已装版本过滤影响（D#645 LOW-3 中的 kind 过滤变异） — 验证：session-init 测试（先红）
- [ ] AC6：仓库门禁：package.json 的 `engines.node` 必须是 `>=X.Y.Z`，并且比下限低一个版本的 Node 会被拦下 — 验证：repo-gates 测试
- [ ] AC7：doctor.md 说明 `needs_node` 通知和 update-state.json 里的 `needsNode` — 验证：测试（先红）
- [ ] AC8：发版核验：`_npmUser` 是 GitHub Actions；sha256 三方一致；签名正反对照；provenance；解包 grep；冒烟：0.20.0 → 0.20.1 真实更新；Node 20 上 `update --force` 被拦下并给出提示

## 方案
- **判断规则**：`unmetNodeRequirement` 只解析 `^>=\s*X.Y.Z$`。0.20.1 及以后的每个更新器都会用这段代码去读以后所有版本的 `engines.node`，所以写法不能变；repo-gates 把 package.json 固定在这种写法上。读不懂的写法不算"Node 太旧"的证据，按原来的行为安装（不加检查前就是这样），以免把所有用户的更新永久卡住。
- **npx/全局**：在 downloadAndInstall 里、validateExtractedPackage 之后、运行 install.js 之前，读解包后的 package.json。这正是即将运行的那份文件，已经过 sha256 和 Ed25519 校验，不需要额外请求。返回值仍是布尔值（现有调用和测试不变），Node 不满足时通过 `onNodeTooOld(range)` 回调告诉 checkForUpdate。
- **插件**：插件模式不下载，所以从 GitHub contents API 读 tag 上的 package.json（`Accept: application/vnd.github.raw+json`；2026-11-02 实测 v0.20.0 返回 200，1.8KB，`engines.node` 是 `>=22.0.0`）。只用于提示；请求失败就退回原来的提示。fetchLatestRelease 多返回原始 `tag`。
- **频率**：和现有的 `failed`、`plugin_update` 一样，更新一直挂着就每天检查、每天写一次通知，不新增节流状态。npx 安装每天会多下载一次 229KB 的包（和 `failed` 时一样）。
- **出路**：升级 Node；或者 `npx gsd-lite@latest install` 直接安装（npm 会提示 EBADENGINE，engine-strict 下会拒绝）。
- **版本号**：0.20.1 补丁版本。Node 22 及以上什么都不变；只有 0.20.0 已经声明不支持的 Node 20 上，更新器开始像 npm 一样遵守 `engines`。D#645 定的也是 0.20.x。
- 提示文字会发给模型（会话提示、doctor.md），所以整个版本按 L3 处理。

## 决策与进展
- 自评（产品 / 设计 / 工程）：价值在于把"静默装坏"变成"装之前告诉用户升级 Node"，并且提示在用户手里的版本还能用时就出现。用户看到的只是一条有明确动作的提示。工程上，npx 路径用已校验的包，不增加网络请求；插件路径只影响提示，失败时退回原状。最大的风险是解析写法被以后的维护者改掉，由仓库门禁兜住。
