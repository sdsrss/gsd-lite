# 0.20.2：更新器在私有临时目录里解包和运行
状态：实现完成，待 PR 和评审

## 背景与目标
`downloadAndInstall`（hooks/gsd-auto-update.cjs:782）把发布包解到 `os.tmpdir()/gsd-update-<Date.now()>`，并用 `mkdirSync(..., { recursive: true })` 创建这个目录。目录已存在时这个调用不报错，直接沿用；随后在这个目录里写包、解包，再从里面运行 `install.js`。在 Linux 上 `/tmp` 是所有本地用户共享的（本机 `drwxrwxrwt root`），另一个用户可以先建好这个路径并让它人人可写。之后受害者解出的 `install.js` 虽然已经过 sha256 和 Ed25519 校验，但在校验之后、运行之前，可以被这个用户替换。结果是以受害者身份执行任意代码。更新器启动后，进程列表里能看到它（`ps`），从启动到建目录要先经过 `gh auth token` 和一次 API 请求，所以要猜中的时间范围只有几秒，也就是几千个可能的目录名。

同一缺陷还解释了 0.20.1 评审时在 Node 26 上偶发的那次失败：并行的测试进程在同一毫秒共用一个目录，先结束的那个把目录删掉，另一个写入时就失败。那次失败没有日志，所以只能说机制能复现，不能确认就是那一次。

仓库已经把共享 `/tmp` 当作不可信位置处理过一次：ctx-bridge.cjs 的文件因为这个原因移出了 `/tmp`（#8）。更新器这里是同一类问题里漏掉的一处，而且这里会执行目录里的代码。

## 范围
- 做：
  - `downloadAndInstall` 改用 `fs.mkdtempSync(path.join(os.tmpdir(), 'gsd-update-'))`：目录名随机，只有当前用户能访问（0700），路径已存在时不会沿用。
  - CHANGELOG 0.20.2；改正 0.20.0 条目里"npm 在每日更新和插件更新时不警告"的错误说法（D#667 第 7 条）。
- 不做（D#667 其余各条的处理见"决策与进展"）：
  - CLI 在插件模式下报 npx 包自己的版本（D#667 第 2 条）：要从多条插件记录里选出正确的一条，0.10.0 在这块两次方案被否，不和安全修复放在同一个版本里。
  - 将来第一个用到 Node 22 特性的版本在旧 Node 上明确报错：仍按 0.20.1 的决定，做那个版本时加；为防止遗忘，写进发版手册。

## 方案
- `let tmpDir = null;`，在 try 里 `tmpDir = fs.mkdtempSync(...)`，finally 里只在 `tmpDir` 有值时删除。`mkdtempSync` 抛错时（TMPDIR 不可写等），走现有的 catch，返回 false。
- 不把临时目录挪进 `~/.claude/gsd/`：install.js 会整体替换那个目录，而 install.js 正是从临时目录里运行的。
- 0.20.2 这次更新本身仍由旧更新器执行；从 0.20.2 开始的更新才用新目录。CHANGELOG 只写"0.20.2 的更新器"做什么。

  - 第 6 条：本版修复。
  - 第 7 条：本版修复。
  - 第 8 条里的 `pluginServesHooks` 只读 `record[0]`：出错时两份 hook 都运行（会被看见），符合"宁可多跑一次也不静默"的设计，不修。用户级插件加遗留 `failed` 提醒多打一次、0.7.6 及更早的 npx 安装：不修。CI 测 22.0.0 和两个项目级插件互相吞提醒：继续推迟（前者要改 CI 配置）。
